# DejaReview Development Guide

## Working Rules

- Keep user installation, workflow, recovery, privacy, and limitations in `README.md`; keep implementation and contributor guidance here.
- The reviewer alone manages staging and reverting, including explicitly activating Stage File or confirming Revert File in Files to Review. Coding agents must NEVER stage, unstage, stash, or invoke revert on workspace changes; the extension exceptions below do not authorize agent staging/reverting or bulk/autonomous source discard. Commit only when the user explicitly requests it, and include only changes already staged by the reviewer; never include unstaged changes or stage files to prepare a commit. Before committing, inspect status, the staged diff, and recent commit history. Preserve existing staged and unstaged work. Read-only `git diff HEAD` shows changes that plain `git diff` hides in the index.
- Treat pasted review feedback as the default task input. Exclude `REVIEW-NOTES.md` and user-local review archives from routine searches. When the reviewer explicitly requests inspection, read only the requested file or archive for that task. Permission to inspect does not authorize recreating, migrating, editing, replying in, or recovering review data; those actions require a separate explicit request. Recovery remains reviewer-controlled.
- Tests may use synthetic in-memory feedback or disposable fixtures, never the user's review data. If the current task prohibits even fixture review-file/archive reads, skip the extension-host suite and report that limitation.
- Keep changes focused; add no compatibility layer without a concrete shipped or persisted contract. Existing archive records are such a contract. Do not introduce legacy scratch-file migration.
- Use Review Note(s) for extension-owned labels, prompts, tooltips, accessible text, and counters. Keep native VS Code comment APIs, internal model names, command/context IDs, and schema fields unchanged unless specifically required.
- Git integration is read-only except for reviewer-triggered Stage File and Revert File in Files to Review: one `Git.add` call for staging or, only after modal confirmation, one `Git.clean` call for reverting, each with exactly one validated host-held file path. Revert File is the authorized source-mutation exception: restore tracked working-tree content from the index or remove an untracked file, never change the index. No automatic or bulk staging/reverting or autonomous source discard; the extension never unstages, stashes, commits, or otherwise changes source code. The optional `.gitignore` update still requires reviewer approval.

## Code Quality

These rules apply to new and materially changed code in this TypeScript VS Code extension, including tests. Keep this guide self-contained. The safety and persistence contracts below remain authoritative.

### KISS: Readable Control Flow

- Optimize for the next reader, not the fewest lines. Use descriptive names, one statement per line, and blank lines between validation, state changes, I/O and publication. Expand multi-step one-line branches and callbacks.
- Keep each function focused on one responsibility. Around 40 lines or more than three nesting levels is a reason to review the structure, not a quota to satisfy by scattering logic into tiny helpers. Keep a cohesive operation together when extraction would make its ordering harder to understand.
- Prefer early returns for invalid or unsupported cases. Use a `switch` for distinct action variants rather than a long, nested `if/else` chain that repeatedly checks the same discriminator.
- Do not use nested ternaries. A simple ternary is appropriate for one small value choice, not selecting action schemas, composing a workflow, or hiding several business rules.
- Split conditions that mix unrelated concerns. Name a predicate when it expresses a useful domain concept, or use separate guards for schema, scope, membership and busy state. Do not merely rename an unreadable expression to `isValid`.
- Keep side effects explicit. Avoid IIFEs inside object literals, assignments hidden in expressions, and conditional spreads that assemble several different action shapes in one payload. Construct each variant directly when that is easier to read.

### DRY: Reuse Without Machinery

- Share logic when it represents the same rule and should change for the same reason. Similar-looking code is not sufficient justification for a generic helper, base class, registry or configurable pipeline.
- Keep helpers local unless another module actually needs them. Extract a helper when it is reused or isolates a coherent, independently testable operation; avoid pass-through wrappers and helpers that only save a line.
- Do not deduplicate away trust boundaries. Client checks improve UX, host checks authorize actions, and post-await checks detect changed state. These are separate responsibilities even when their conditions look similar.
- Keep one source of truth for each session, snapshot and projection. Derive display state rather than maintaining parallel flags that must be synchronized. Do not cache cheap values or add compatibility paths without a concrete need.

### Types And Message Boundaries

- Use TypeScript for new source and test files. Prefer named exports and explicit return types for named functions and methods; allow inference for obvious inline callbacks. Prefer `type` for new unions and object shapes, but retain existing interfaces where appropriate rather than rewriting them for style alone.
- Use discriminated unions when variants require different fields. Prefer `{ type: 'edit'; noteId: string } | { type: 'addGeneral' }` over one object with every possible field optional. Do not invent file fields for general notes.
- Receive external data as `unknown`. Narrow it with runtime checks; do not use `any`, non-null assertions or `as Action` to bypass validation. Use `Record<string, unknown>` for an inspected object, not as a substitute for a typed internal model.
- Keep message-shape validation, live-state authorization and execution distinguishable. Decode exact allowed keys and field types into a typed action, then check its current folder/session/membership before dispatch. Reject unknown actions and unexpected fields; do not weaken validation to shorten the handler.
- Group action cases only when their rules really match. For dashboard handlers such as `receiveMessage`, prefer a straightforward action switch with focused validation over nested category booleans, ternary-selected key lists and a final cast-built payload. Do not introduce a schema library or generic routing framework for this small protocol.
- Preserve explicit post-await and pre-publication guards when extracting validation. A successfully decoded message does not prove that its saved target or folder is still current.

For example, make an action's required data visible in its type and use ordinary narrowing:

```ts
type EditorMessage =
  | { type: 'input'; editorId: string; body: string }
  | { type: 'cancelEdit'; editorId: string };

function isEditorMessage(value: unknown): value is EditorMessage {
  if (!value || typeof value !== 'object' || Array.isArray(value)) {
    return false;
  }

  const message = value as Record<string, unknown>;
  if (typeof message.editorId !== 'string' || !message.editorId) {
    return false;
  }

  switch (message.type) {
    case 'input':
      return Object.keys(message).length === 3 && typeof message.body === 'string';
    case 'cancelEdit':
      return Object.keys(message).length === 2;
    default:
      return false;
  }
}
```

This example checks shape only. Real dashboard messages also require folder scope and live host-held session authorization; those checks must not be replaced by the type guard.

### Async, Errors And Formatting

- Prefer `async`/`await` for sequential work. Use promise chaining only where it makes queueing or fire-and-forget rejection handling clearer. Make ownership, busy-guard acquisition, revalidation and `finally` cleanup easy to follow.
- Throw useful errors from operations that cannot complete; translate them into user-facing messages at the owning UI boundary. Distinguish expected rejection/cancellation from failure. Never swallow a failed write or log raw feedback/archive contents.
- Comments explain a non-obvious reason, invariant or API limitation. Add concise TSDoc for non-obvious exported contracts, not boilerplate documentation on every self-explanatory function or field.
- Keep the repository's two-space indentation and the surrounding file's quote style. Use braces and readable multiline formatting for nontrivial branches, objects and conditions. Do not mix unrelated formatting churn into a behavior change.
- Group Node/VS Code imports and local imports consistently; use type-only imports where suitable. Add no runtime dependencies or tooling solely to enforce these guidelines. Keep native VS Code APIs, webview DOM APIs and theme tokens rather than importing the adjacent project's UI framework or conventions.

### Tests And Refactoring

- Test observable behavior with clear arrange, act and assert sections. Cover valid actions, invalid boundary input, stale state, cancellation and failure without hiding the important steps inside an all-purpose test harness.
- Use small local fixtures; share larger fixtures only when it removes real repetition. Prefer explicit expected values and complete result shapes over expectations computed using the same implementation being tested.
- Model runtime-invalid input at the actual `unknown` boundary. Keep internal mocks structurally checked with target-derived types such as `Pick` or `satisfies`; avoid double assertions and impossible internal states unless the test deliberately exercises that boundary.
- Use deferred promises/events to test races, not arbitrary sleeps or longer timeouts. Keep exact string/CSS/CSP assertions where those are deliberate contracts, but do not freeze incidental helper names or code layout in tests.
- Refactor the touched behavior incrementally, preserving exact schemas, saved bytes, input retention and concurrency guards. Do not turn a small change into a repository-wide style rewrite. Run the relevant regressions and report what was actually verified; adding this guide alone does not make existing code compliant.

## Architecture

TypeScript extension for VS Code 1.96+, package `dejareview`, ID `local-review.dejareview`, command/settings prefix `dejareview.`. Requires the bundled `vscode.git` extension and a containing local Git repository. Runtime npm dependencies are zero.

| File | Responsibility |
| --- | --- |
| `src/extension.ts` | Activation/disposal, commands, native drafts and saved threads, status, note navigation/actions, decorations/hover, input guards, refresh scheduling and generations |
| `src/model.ts` | File/general note models, ReviewComment, ParsedComment, ResolvedAnchor, Resource, Origin, Side, Comparison and validation |
| `src/parser.ts` | Markdown scanning, file notes and separate generalNotes with combined ordered parsedNotes, base recognition, diagnostics and exact block offsets |
| `src/writer.ts` | File/general append, targeted body edit/delete, file-only explicit line-number rewriting |
| `src/anchor.ts` | Content-based re-anchoring |
| `src/git.ts` | Git discovery, workspaceRepository adapter, origin/resource resolution and blobs, scoped unstaged/untracked candidates and per-file stats, validated single-file staging via `Git.add` and index-preserving revert via `Git.clean` |
| `src/editorContext.ts` | Frozen editor source/range, comparison picker, side/origin capture and snippet elision |
| `src/store.ts` | Saved-file reads, watcher/save notifications, serialized mutations, dirty/snapshot/symlink guards and handoff/recovery I/O |
| `src/handoff.ts` | Pure copyAndClear port, exact instruction and partial-success result types |
| `src/archive.ts` | Folder-scoped JSON archives, atomic publication, validated listing/reading |
| `src/dashboard.ts` | Webview provider, host-held general-create/any-note-edit sessions and input guards, Files to Review projection, combined note-card previews, explicit editor-body payloads, archive display metadata and validated reviewer-triggered Revert File/Stage File actions, revert modal/dirty-buffer guards and shared busy guard |
| `src/dashboardHtml.ts` | Themed responsive dashboard shell, styles, toolbar/menu, floating note editor and restrictive CSP; embeds the compiled client |
| `src/dashboardClient.ts` | Type-checked, self-contained webview client serialized after compilation; keyed rendering, runtime message validation, request-correlated input acknowledgements and pending submission retention |

The parser, writer, anchor, port-based handoff and dashboard HTML are usable without a VS Code host. Native file-note capture/editing stays in `extension.ts`; the single Review Notes webview panel also composes general notes and edits any saved note through a floating modal. It handles Files to Review and reviewer-triggered single-file staging/reverting, current note cards, navigation, deletion, handoff and explicit archive history/recovery. There is no separate tree view or editor panel. No AI service, account, PR integration, MCP server, daemon, agent replies, acceptance tracking, hunk inventory, or completion inference is in scope. The sole exception for candidate selection is the user-defined Files to Review files-only heuristic below; it is not hunk tracking, approval, or completion inference and adds no persistent completion state.

## Workspace And Git

- Scope everything to `vscode.workspace.workspaceFolders?.[0]`, deterministically. No picker, active-editor switching, arbitrary-repository fallback, or fallback to another workspace root.
- The opened folder owns `REVIEW-NOTES.md`, its watcher, paths, archive namespace, store, dashboard and mutation guards, even when it is a Git subfolder. Create notes lazily on first submission or explicit recovery, not activation.
- `workspaceRepository()` exposes the opened folder as `rootUri` and delegates Git state/events, commit resolution, revision operations and the single-file `Git.add`/`Git.clean` exceptions to the containing Git repository. Translate workspace-relative paths only at the Git boundary, including staging and reverting. For `/repo/packages/app`, save `src/a.ts` while querying the parent Git resource `packages/app/src/a.ts`.
- Require local `file:` folders in a containing Git repository for all notes, including general notes. File-note capture additionally requires supported `file:`/`git:` text resources; general creation requires no active file, selection or resource and must not fabricate one. Files to Review staging also supports binary, new and deleted files without requiring readable text or available stats; revert supports standard tracked/untracked candidates subject to the dirty-buffer and index-preservation guards below. Reject outside-folder resources, other roots, nested separate repositories and cross-boundary comparisons. Discovering only a nested repository does not make a folder supported.
- Wait for Git initialization and retry discovery on relevant Git events. Workspace changes invalidate obsolete refreshes/actions and defer safely while mutations are busy; never retarget captured drafts or in-flight writes.
- Resolve origin separately from comparison side. `file:` means `changed`; Git query ref `''` means `staged`, `HEAD`/`head` means `head`, and `~` means index only when the absolute file URI belongs to `repo.state.indexChanges`, otherwise HEAD. Other supported refs resolve through `getCommit` to `commit:<full-sha>`.
- Git URI queries are an implementation detail: validate malformed/unavailable refs rather than guessing. Use absolute resource URIs for index membership and ownership checks.
- Reject filesystem paths through symlinks below the containing Git root, including aliases into the same scope, and literal POSIX backslash filenames that cannot be represented without identity loss. Keep persisted Markdown slash normalization separate. Metadata checks and final leaf revalidation reduce observed races, but are not atomic with external filesystem changes.
- `.gitignore` suggestion state is scoped by opened folder URI and the current scratch filename suffix.

## Markdown Contract

The saved file is the sole source of current review feedback. Note UI is a full parse/resolve projection; Files to Review combines that saved-note projection with current Git state. Archives are not current feedback until explicitly recovered. Never regenerate the whole file from the parsed model.

```text
document   := preamble? note*
note       := comment | general
general    := "## General Review Note" newline body
comment    := header context anchor? body
header     := "## `" path "`:" (range elision? | "file")
elision    := "; Snippet: elided"
range      := positive-int | positive-int "-" positive-int
origin     := "Working tree" | "Staging area" | "HEAD" | "Commit " full-sha
context    := document-selection | comparison newline comparison-selection
document-selection   := "Selected: " origin
comparison           := "Comparison: " endpoint " -> " endpoint
comparison-selection := "Selected: " side " (" origin ")"
side       := "Original" | "Modified"
endpoint   := origin | "`" path "` (" origin ")"
```

- General notes use the exact header `## General Review Note` and body only: no path, range, context, origin, comparison or anchor. A leading code fence is body content, never an anchor. Metadata-like prose remains body text. Apply body-wrapper encoding/decoding and preservation to both note kinds; never give general notes synthetic file identities or anchoring state.
- Whole-file notes use `## \`path\`:file` and document `Selected:` context with a body, never a comparison, anchor or elision. Keep them in `comments` for saved-path filtering and combined operations. `wholeFile: true` distinguishes scope; internal line hints are fixed at 1, never serialized, displayed, resolved into native threads/decorations, or rewritten. The dashboard creates them with Working tree origin from a host-held Files to Review candidate, without reading source content. Whole-file cards display just the filename and navigate to the file (index for an unstaged deletion).
- Keep parsed general notes in separate `generalNotes`, retain the file-note collection for file-only consumers, and expose `parsedNotes` as both kinds merged in saved-document order by exact offsets. Use combined identities for cards, targeted body edits/deletions and duplicate/stale snapshot checks. Total UI and newly created archive `commentCount` values include both kinds. File path filters, capture, resolution, native threads/decorations and line-number rewriting remain file-only. Preserve historical archive counts without recounting or migration.
- The optional H1 carries a short base SHA; preserve the writer's existing preamble format. If HEAD moves from the recorded base, HEAD/index file notes become suspect and stale with a warning, not automatically rebased. General notes do not become stale from HEAD movement.
- Paths are opened-folder-relative POSIX paths; accept backslashes on read and normalize on write. Ranges are 1-based inclusive in the selected origin. Keep internal origin/side values unchanged; readable labels are the serialization format.
- File-note context is required immediately after the header, allowing blank lines before and between metadata lines. A document-selection file note uses `Selected: <origin>`. Comparisons use `Comparison: <Original endpoint> -> <Modified endpoint>` followed by `Selected: Original (<origin>)` or `Selected: Modified (<origin>)`. Same-file endpoints omit paths; different-file endpoints name both paths. Always serialize an explicit side and selected origin, even for identical endpoints; never infer or omit the side. Validate that the selected side's endpoint matches the header path and selected origin. Side is provenance, not acceptance.
- A file-note anchor is only the immediately following code fence after `Selected:`, allowing blank lines. Prose before a fence means no anchor. File context is reserved and body edits cannot replace it. Parse only the explicit file format; old compact contexts are malformed but preserved. No legacy header/comparison parser or automatic migration; historical raw bytes remain untouched.
- Track backtick and tilde fences, including longer runs. Only an unfenced `##` starts a block. Tolerate file-header whitespace and case-insensitive origin/side labels; the general header remains exact. Full commit hashes may be 40 or 64 hexadecimal characters.
- Duplicate headers are distinct notes. Preserve unknown sections, malformed blocks, preamble text, BOM, CRLF and other original formatting; publish diagnostics instead of guessing malformed metadata or dropping feedback.
- Append preserves preceding bytes. Body edits splice only the body and preserve comparison metadata and sibling blocks. Deletion removes the target block and exactly one following blank separator. Preserve BOM-aware splice offsets.
- Composer bodies accept arbitrary text, including unfenced `##` headings, metadata-like lines and unbalanced fences. Keep safe prose plain; protect ambiguous bodies and significant boundary whitespace with an exact `Body: fenced` line followed immediately by a backtick fence labeled `markdown`, longer than any backtick run in the body. Add/remove exactly one structural newline before its closing fence; preserve body whitespace while normalizing line endings to the destination file as before. An anchorless leading fence also needs this wrapper. Decode only the exact marker at the body start, once, and require the closing fence to end the body. Body splice offsets include the wrapper; the model/UI body excludes it. Malformed manually edited wrappers produce diagnostics, never discarded trailing feedback. Copy/archive still use raw saved bytes, including wrappers; do not regenerate them.

## Capture And Anchoring

- These capture and anchoring rules apply only to file notes. General notes remain body-only dashboard entries and participate in saved-note operations, counts and handoff, never code navigation or re-anchoring.
- Capture path, side-local range, origin, side, ordered comparison pair and original whole-line snippet. No selection means current line. A selection ending at column zero excludes that final line; native thread ranges include their end line.
- Keyboard/menu entry freezes source context before asynchronous UI and before typing. Never use whichever editor is active at submission to retarget a draft. Unsaved source buffers can provide captured text without saving or changing source.
- Preserve up to 20 lines verbatim; longer ranges store first 10, a bare `...`, and last 5 while retaining the full range and marking the header `; Snippet: elided`. This is fixed, not configurable. Elision requires the explicit marker and that snippet shape but survives range shrinkage. Match both endpoints, allowing omitted length to change. Unmarked ellipses are literal snippet content.
- Freeze comparison endpoint identities before context UI and verify displayed Git text against its resolved revision. Revalidate captured ownership and mutable revisions after waits and before submission publication; preserve input on failure. Empty opposite panes in added/deleted comparisons need identity validation, not readable absent blobs.
- Re-anchor against the selected origin, using the open buffer for `changed` when available. Try the recorded position, local search (default +/-50 lines), then whole-file search. Strip trailing whitespace and use a common-indentation-insensitive fallback. Ambiguous matches choose the nearest with low confidence; no anchor uses low-confidence line hints; no match is stale.
- Never search the opposite comparison resource as fallback. Stale notes remain as dashboard cards and in the clipboard but have no anchored thread/decoration. Never automatically delete or rewrite them.
- Re-anchoring normally updates only display positions. Persist header range changes only for explicit `dejareview.reanchorAll`. Resolve batch identities against a single initial snapshot, then splice in reverse order so duplicate notes remain distinct.

## Persistence And Concurrency

- Watch the opened folder's root file and handle save events, explicit refresh and mutations. Unsaved notes are not parsed; source-buffer changes may re-anchor. Missing notes clear saved projections without recreating the file or restoring archives. Preserve input during refresh.
- Debounce/coalesce notifications. Explicit writes refresh; watcher reads never write, so duplicate reads are harmless. Do not add last-written suppression or promise exactly one parse or fixed refresh latency.
- Generation tokens prevent obsolete async refresh publication. Action arguments carry the entry, folder scope and exact saved snapshot, not a semantic stable ID.
- Before a stale edit/delete/reveal, reparse the saved snapshot. Use the index only if snapshot and raw block match; otherwise require a uniquely matching exact raw block in both old and current parses. Reject ambiguous duplicates or changed entries, preserve edit input and ask to refresh.
- Dashboard create/edit input is host-held and folder-scoped, not owned solely by a webview DOM or current projection. Retain the active session, current body and captured edit target across refresh and panel hide/recreation within the extension session; do not promise persistence across extension/window reloads. Refresh must not replace typed input with saved text or retarget an edit to a newly assigned card ID. Scope changes must never publish old input into another folder.
- Permit only one active dashboard editor session. Validate session identity, mode, folder and busy state on input, Save and Cancel messages; reject late messages from closed/replaced sessions. An edit binds to the host-held saved entry and original snapshot/raw block, revalidated after waits and immediately before publication. General creation still validates the supported folder and saved snapshot. Failed validation or save retains input; clear only on successful save or explicit Cancel/Escape. Reject empty/whitespace-only new submissions and concurrent/repeated saves. Do not silently replace an active editor with another card or create action.
- Serialize mutations per opened folder. Dirty review buffers block writes with Save and retry / Cancel. Publish mutations and recovery via sibling temporary files and rename after rechecking snapshot, symlink, file and input guards; partial temporary writes must not truncate live feedback. Clean up failed temporary files where possible; never write under unsaved feedback.
- `workspace.fs` has no atomic compare-and-write/delete against external writers. Rechecks protect observed changes but cannot eliminate the final filesystem race. Do not claim transactional clearing/recovery.

## Handoff And Archives

Keep `HANDOFF_INSTRUCTION` in `src/handoff.ts` and its exact-string test synchronized. The current instruction is:

> Address the review feedback below using the file paths, captured snippets, and Original/Modified comparison context. Paths are relative to the opened project folder; locations and snippets may be stale. All explicitly approved changes are already staged. Never stage or unstage anything; only the reviewer manages staging. Summarize your changes in this conversation.

1. Validate folder scope, busy state and known drafts/edits. An active dashboard editor blocks handoff until the reviewer finishes or explicitly cancels it; do not offer discard-on-success for this editor. Preserve the existing native-input choices: finish, explicit discard-on-success, or cancellation. Dirty review buffers require save/retry or cancel. Recheck input guards after asynchronous waits and before clearing.
2. Read the complete saved raw snapshot. Missing/whitespace-only content leaves clipboard and file untouched. Malformed/free-form feedback remains meaningful even with zero parsed notes.
3. Copy instruction plus raw text, including stale/malformed content and captured snippets. Await clipboard success.
4. Durably archive the exact raw snapshot without the instruction using temporary JSON plus atomic rename without overwriting an archive. Await success before clearing.
5. Recheck dirty state and source snapshot, then delete only the opened folder's notes file. Concurrent changes retain live feedback and the archived snapshot. Failures report partial success explicitly; do not restore or clear the clipboard.
6. Only after successful clearing, clear saved projections and explicitly authorized native input. Keep unobservable native drafts alive. A new submission of either note kind creates a fresh base unless a batch was recovered first. Do not automatically open archive history after clearing.

Archives use `globalStorageUri/reviews/<sha256(openedFolderURI)>/<uuid>.json`. Preserve the existing version and fields: `version`, `id`, `repoUri`, `text`, `createdAt`, `commentCount`. Legacy `repoUri` holds the opened folder URI; do not rename it or migrate records. Validate IDs, identity, URI, dates, counts and text; invalid/path-like IDs cannot access arbitrary files. Skip invalid list records.

Git-root namespaces stay compatible; subfolder namespaces are isolated. Never scan other namespaces or rewrite historical raw contents, paths or filename mentions. Archive counts are historical nonnegative safe integers, not assertions against the latest parser; newly archived counts include file and general notes. History is hidden by default and opens only through the internal toolbar's More actions (...) menu, Recent Archives item, when no meaningful raw feedback is active. Include a close control. When opened, show the latest 10 valid batches newest-first with display metadata and recovery actions, but retain all older batches. Preserve command-based recovery independently of history visibility. Coalesce concurrent listings and cache only display metadata by file mtime/size, never raw feedback. Recovery fully revalidates actual contents. Sanitize parse errors rather than logging raw JSON excerpts. No purge, archive-delete action, synchronization or encryption is provided.

Recovery is explicit and keeps the archive. Refuse active feedback, dirty buffers, known drafts/edits (including any active dashboard editor), busy mutations and changed snapshots. Require finish/cancel for dashboard input, including command-based recovery; recheck input guards after waits and before publication. Restore exact raw text, including BOM/CRLF and original base, only into an absent or unchanged whitespace-only file. Never merge or silently overwrite. Reparse/refresh only after restore; never recover automatically on activation or an empty file.

## Files To Review

- Place Files to Review immediately after the conditional Copy Review Notes & Clear action and before current note cards, below the internal dashboard toolbar. Preserve native file composing/editing alongside dashboard general creation and any-note editing. Add no commands, settings, or dependencies; Git integration remains read-only except for the reviewer-triggered Revert File and Stage File icons described here. Confirmed single-file revert is the authorized source-discard exception.
- Candidates are the deduplicated union of `workingTreeChanges` and `untrackedChanges` scoped to the opened folder, filtered to paths with zero parsed saved file notes whose normalized header path matches the candidate. Count every such file note regardless of origin, comparison side, or stale resolution; do not count the opposite comparison endpoint as another header path. General notes never suppress file candidates. Unsaved drafts do not hide candidates. Malformed notes cannot reliably associate a path: do not guess from raw headers or change their preservation/copy behavior.
- Do not union in `indexChanges`: index-only files are absent, while partially staged files remain eligible if residual unstaged changes exist and no parsed saved note matches. Refresh automatically on Git state events, including staging/unstaging, and saved-note projection changes. Apply existing folder/generation guards to asynchronous candidate/stat publication.
- Publish validated candidate snapshots before loading statistics. Background stats enrich existing host-held rows without replacing action identities or changing membership; show Loading stats for new rows until settled, never block Stage File/Revert File on counts. Existing same-resource rows retain their last display during revalidation, including unavailable counts; failed stats settle to unavailable, not stale numeric counts. Bound and serialize stats jobs, stop obsolete batches, and guard publication by folder, snapshot and stats revision. Editor-only refreshes may retain stats for identical candidates; Git/saved-note events invalidate the projection and revalidate per-file cache inputs. Cache only successful numeric counts with observed disk metadata and, for tracked files, index object/mode signatures; prune to current candidates and scope. Explicit refresh bypasses that cache, retaining the force request through superseded jobs. Post-action refresh does not add a second forced stats invalidation. Discovery errors retain candidates, update visibility, and settle orphaned loading flags. Membership lookup caches are operation-local, invalidated by Git events, and freshly rebuilt before publication; mutation authorization remains independent and live.
- Keep no persistent completion flag. Successful copy-and-clear, clearing saved notes, or deleting the last note on a path intentionally makes otherwise eligible files reappear for the next review/AI iteration. Empty means no current candidates, never approval or completion. This is a user-defined files-only heuristic, not a hunk inventory or acceptance model.
- Derive the heading count and resolved WebviewView badge from current candidate rows, not notes or exiting DOM nodes. The badge displays the file count, includes file and combined saved Review Note counts in its tooltip, and is absent at zero/no folder. No custom Activity Bar colors, extra views or commands. Derive visible-file highlights from validated resources in visible text editors, including Git panes; hidden documents do not count and split panes may mark multiple paths.
- Publish the host-held target row's staging/reverting state before asynchronous work and retain it through immediate post-action refresh. Keep the shared action guard and do not dim the whole panel or reveal hidden action icons. Collapse only confirmed same-folder removals with inert exiting rows; cancel exits on reappearance, remove immediately on folder change or reduced motion. Operational candidate-discovery/ownership errors must propagate so the last known list is retained with an error rather than falsely confirming removal; stats-only errors still show Stats unavailable. Never replace Git confirmation with a timed optimistic removal.
- Visible file rows use only a theme-token background highlight, without an eye icon. Pending state must not change row geometry: use an inset accent and visually hidden accessible status rather than a loading line or layout-changing border, including during collapse.
- Clear native badges by publishing zero with an empty tooltip before assigning undefined. Supported older VS Code hosts retain the previous activity on undefined alone; zero hides its NumberBadge. Cover the rendered activity state, not only the extension-side badge property.
- Tracked-file addition/deletion stats use Git's per-file index-to-worktree diff, translated at the opened-folder Git boundary and based on saved disk contents, never unsaved editor buffers or HEAD-to-worktree totals. For new untracked text, count additions using LF-based line counting with a fixed 5 MiB read limit. Binary files, over-limit untracked files, and unavailable results display Stats unavailable, not fabricated zero counts.
- File rows display Added, Removed, or Renamed from current index-to-worktree Git status, never inferred from numeric statistics or source similarity. Untracked/intent-to-add files use Added; working-tree deletions use Removed; Git-reported unstaged renames use Renamed. Never derive labels from `indexChanges` (HEAD-to-index history): residual edits after a staged addition or rename use ordinary modified-file counts. Keep labels through loading/unavailable statistics, omit zero counts on labelled rows, retain nonzero counts on both sides and ordinary +N -N counts on modified rows. Preserve read-only status derivation, keyed row identity and host/client payload validation.
- File activation opens the unstaged diff for a tracked file, the file for an untracked file, or the index revision for a deleted file. Validate current folder ownership and candidate membership in the host before navigation; do not trust client-supplied paths or use another root as fallback.
- Tracked Files to Review diffs use VS Code Git's working-tree comparison URI (`ref: '~'`, serialized after `path`) so native Stage Hunk/Selection menus are available. Construct it only from validated endpoints. Keep explicit persisted staging origins and deleted-file navigation on `ref: ''`; opening a diff never invokes a staging command.
- Each file row offers Revert File, Add File Review Note (note-bubble icon), then Stage File in visual and keyboard order. The icon buttons overlay the top-right corner without reserved row space, appear on hover and `:focus-within`, and remain keyboard-focusable. Tooltips and `aria-label` match those labels exactly. Add File Review Note opens the host-held floating editor for that validated candidate; Save rechecks scope, ownership, candidate membership and saved snapshot before publication, retaining input on failure. Stage File needs only explicit activation; Revert File requires modal confirmation.
- Only staging the first current row arms a single next-file navigation. Wait for successful staging and a refreshed same-folder projection confirming the target is absent from Git candidates, then open the first remaining candidate through the normal validated file-navigation path. Handle delayed Git publication; never advance optimistically, after failure/revert/lower-row staging, on note-based filtering alone, or with no next file. Another dashboard action cancels the pending advance. Keep navigation serialized and consume the intent once; add no persistent selection/completion state.
- Before revert, validate the action schema, current folder scope, ownership, current candidate membership, supported Git state, dirty-buffer status and busy state in the host. Resolve only to a host-held candidate, never a client-supplied path. The modal identifies the target and warns that its unstaged disk changes will be discarded; for untracked files explicitly warn that the file will be removed and cannot be recovered by Git. Cancellation makes no Git call or source change. After confirmation and any asynchronous waits, revalidate scope, ownership, current membership, supported Git state and dirty-buffer status before calling `Git.clean` exactly once with exactly that one validated file path at the containing-repository boundary. Reject stale/cross-folder or changed-state actions rather than retargeting confirmation. Never pass a directory, wildcard, all-files argument or multiple paths; all candidate exclusions below apply.
- Revert tracked working-tree content from the index, not HEAD, leaving every staged change intact, including in partially staged files. Restore unstaged deletions; staged deletions remain staged and are not restored. Remove standard untracked files only after the explicit warning and confirmation. Support standard tracked/untracked binary, new and unstaged-deleted files even without readable text or available stats. Restrict conflicts, intent-to-add and other nonstandard states whenever `Git.clean` cannot preserve the index; reject unsupported or uncertain states, with no index-mutating fallback. Do not use reset, unstage/re-stage, bulk clean, direct source writes/deletes, or buffer-discard commands to implement revert.
- Any dirty editor buffer for the target blocks revert, both before and after confirmation and immediately before Git work. Never save, discard, or otherwise modify editor buffers as part of revert. Revert adds no Review Note and no reviewed/completion flag.
- Before staging, validate the action schema, current folder scope, ownership, current candidate membership and busy state in the host. Resolve the action to a host-held candidate, never a client-supplied path, and call `Git.add` with exactly that one validated file path at the containing-repository boundary. Never pass a directory, wildcard, all-files argument or multiple paths. Support binary, new/untracked and deleted files even when stats are unavailable; all candidate exclusions below also apply to staging.
- Stage the whole file's current disk state, including all residual unstaged content in a partially staged file or its deletion, not selected hunks or unsaved editor buffers. Do not save or mutate source, add a Review Note, or persist a reviewed/completion flag. No automatic or bulk staging, unstaging, stashing or committing is allowed.
- Set a shared host-side busy guard across all file rows before any asynchronous staging/revert work, including revert confirmation, and hold it through Git work. Disable both actions while busy and reject repeated activation or concurrent Stage File/Revert File requests in the host, not just the client. Refresh through Git state with existing folder/generation guards; do not optimistically remove the row. Either action removes it only when refreshed Git state shows no residual unstaged/untracked changes. On failure retain the candidate and report the error. Release busy state on success, cancellation, validation rejection and failure so the reviewer can retry.
- Exclude outside-folder resources, other roots, nested separate repositories, `REVIEW-NOTES.md`, and archives from candidates, stats reads, staging and reverting. Reuse the current parsed saved-note projection for filtering; do not scan/read review files or archives for discovery or stats. Archive contents do not suppress candidates. Existing archive namespaces, retention, visibility, handoff and explicit recovery contracts are unchanged.

## UI And API Limits

- Native multiline comments are single-note containers; disable replies after submission. No resolution state or separate thread store. Apply projections to every matching visible editor, not just the active editor.
- Resolve diff side using full URI (including query) against ordered `TabInputTextDiff` endpoints. Ask when uncertain or same-URI; scheme, path and viewColumn alone cannot identify the focused side. Match display resources by folder/repository, path and origin, not text or path alone.
- Stable APIs expose neither native gutter draft creation context nor all unsubmitted drafts. At native submission, capture then-current source text and infer context only when the full URI belongs to one distinct open editor/comparison context. Deduplicate identical split views; ask for multiple contexts, same-URI comparison sides, or absent context. Do not infer provenance from whichever tab is active after typing. This is submission-time inference, not a guarantee of gutter-creation provenance. Copy excludes unsaved composer text; preserve unobservable drafts for the next pass, without promising persistence across reloads.
- Native threads are URI/range scoped, not pane scoped. Same-URI comparisons can show a thread on both sides. Inline Original-side placement is unreliable. Only explicit Open Side-by-Side Comparison may invoke `toggle.diff.renderSideBySide`; normal navigation must not change layout or substitute the Modified side.
- Preserve capture labels even when the revision is later shown on another side. Clicking a file-note card opens code or reopens its ordered comparison; stale file cards fall back to their saved Markdown block through internal navigation, not a user-facing reveal command. Clicking a general card opens its dashboard editor, never code navigation. Cards have no dedicated Open Comparison action; preserve the native Open Side-by-Side Comparison command (`dejareview.openComparison`), not a global removal. Offer selected-revision navigation when exact pane placement is unavailable.
- Every saved card, including general and stale file notes, offers top-right Edit Review Note then Delete Review Note icons in visual and keyboard order. Both reveal on hover and `:focus-within`, remain keyboard-focusable, and have tooltip/`aria-label` exactly Edit Review Note and Delete Review Note. Icon activation must not trigger card navigation. Edit opens the floating dashboard modal for that saved body only, preserving file metadata/anchor. Delete requires modal confirmation; after confirmation and before deletion, revalidate folder scope, note membership and exact saved snapshot using the existing raw-block checks for either note kind.
- The internal top dashboard toolbar offers Add General Review Note and More actions (...); these are webview actions, not new commands or view-title contributions. Add General Review Note opens a floating webview modal without requiring an active file. Native shortcut/gutter capture remains the path for line-specific creation, while Files to Review offers whole-file creation; native line-note editing remains supported. The same dashboard modal edits any saved note, with Save, Cancel and Escape cancellation; use an accessible labelled dialog, keyboard focus containment and restoration, and theme tokens. Treat body text as literal editable input, not HTML. A failed save leaves the editor and input intact. Hidden or refreshed panels reconstruct the active editor from host-held session state.
- Use untrusted Markdown for bodies, hovers and tooltips (`isTrusted = false`, `supportHtml = false`); no executable links from user feedback. Badges are `[review]` at the first resolved line with an overview-ruler mark; duplicate notes retain separate identities.
- Dashboard fills the single Review Notes panel with an internal top toolbar, combined parsed count, conditional copy action, Files to Review immediately after copy and before current note cards, and explicitly opened archive history, with no repository heading/selector. Cards follow combined `parsedNotes` document order. Each card shows only a filename/line header or General Review Note header and the first two body lines, clamped to at most two visual lines even in narrow sidebars and truncated as needed, plus hover/focus Edit then Delete icons. Show no visible directory, context or status labels and no dedicated comparison action. Initially hide copy; show it for meaningful raw feedback even with zero parsed notes, disabling rather than hiding it while busy. Copy explanation is tooltip-only. The panel title offers only refresh, not copy, general creation or More actions.
- More actions (...) opens an accessible keyboard-operable menu containing Recent Archives. Mark Recent Archives unavailable with `aria-disabled` while meaningful raw feedback is active, but keep it focusable and activatable to explain that the reviewer must finish the current review and use Copy Review Notes & Clear first; do not open history. Raw text, not parsed count or Files to Review candidates, controls eligibility. History is hidden by default even when empty or after handoff, opens only on explicit selection and has a close control. Hide history when meaningful feedback becomes active; returning to empty must not reopen it automatically. Closing history does not delete archives. Host validation must reject history/recovery requests that are stale, cross-folder, disallowed by current mode or busy state, regardless of client visibility. Recovery commands remain available with the same host guards.
- Navigation keeps host-side action serialization without publishing a dashboard-wide busy state. Mutations still disable actions and retain the shared host guard, but must not dim the whole panel or reveal hidden row icons. Keep keyed rows and hover styling stable across busy updates.
- The primary Copy Review Notes & Clear button is full-width and at least 48px tall. Use VS Code theme/focus/high-contrast tokens, accessible labels, keyboard controls and narrow-sidebar wrapping. History shows local dates and singular/plural review-note counts, including zero.
- Webview uses nonce-based restrictive CSP, no remote resources and text-only rendering for metadata and current note previews. Normal projection/card payloads contain only the first two body lines, bounded to at most 320 characters total, never full bodies, anchors, raw saved text or archive feedback. The sole full-body exception is an explicit active dashboard editor payload for the host-validated create/edit session, including restoration of that session after refresh/hide. Send only that editor's body, not other saved bodies, captured anchors, raw blocks/snapshots or archive text. Do not preload full bodies in cards, hidden DOM, data attributes or general refresh payloads.
- Validate action schema, current folder key, note ID and its membership in the host-held projection, associated folder scope and exact saved snapshot, archive membership, editor session/mode and busy state again in the host. Note IDs are projection-scoped handles, not semantic stable identities; resolve them to host-held entries and apply saved-snapshot/raw-block checks before navigation or mutation. Dashboard input messages may supply editable body text only for their validated active session; never trust client-supplied target paths, ranges, metadata or snapshots. Stale/cross-folder actions must fail safely. Copy/recovery guards must see host-held dashboard input even when the panel is hidden, without changing native draft discard-on-success behavior.
